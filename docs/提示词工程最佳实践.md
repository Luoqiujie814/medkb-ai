# 医药领域AI信息抽取 — 提示词工程最佳实践

> 版本: v1.0 | 更新日期: 2025-05-29 | 作者: 罗秋杰

---

## 1. 概述

本文档沉淀了在MedKB-AI项目中针对医药文本信息抽取场景的提示词工程（Prompt Engineering）实践经验，涵盖三种主流策略的系统对比、关键设计原则和可复用模板库。

### 1.1 使用场景

| 场景 | 推荐策略 | 说明 |
|------|---------|------|
| 快速原型验证 | Few-shot (3示例) | 10分钟内产出可用结果 |
| 高精度知识抽取 | 结构化JSON输出 | 生产环境首选 |
| 复杂语义关系 | Chain-of-Thought | 需要推理链的复杂场景 |
| 混合场景 | 结构化JSON + CoT指导 | 在格式规范中嵌入推理步骤 |

## 2. 三种Prompt策略深度对比

### 2.1 策略一：Few-shot (3示例)

#### 设计原理
通过在Prompt中提供3个精心设计的标注示例，让模型学习标注格式和规范。

#### 优势
- ✅ **冷启动快**：无需复杂Prompt设计即可获得基本可用的结果
- ✅ **Token效率高**：System Prompt相对精简
- ✅ **灵活性强**：修改示例即可适应新领域

#### 劣势
- ❌ **一致性差**：不同文档间输出格式可能有波动
- ❌ **格式漂移**：偶尔脱离JSON格式输出
- ❌ **示例偏差**：示例的选择会影响模型行为偏向

#### 实测数据（医药文本100条）
| 指标 | 得分 |
|------|------|
| 实体F1 | 0.82 |
| 关系F1 | 0.75 |
| Schema合规率 | 60% |
| 平均Token消耗 | 1,850 |

#### 适用场景
- 新领域的快速探索
- 标注格式不确定时的实验
- 预算有限的场景

### 2.2 策略二：Chain-of-Thought (思维链)

#### 设计原理
要求模型"先推理、再输出"，在输出最终标注答案前展示推理过程。

#### CoT推理框架
```
步骤1：通读全文，理解文本类型和主题
步骤2：逐句扫描，标记所有药品名称 → 标准化通用名
步骤3：标记所有疾病/症状 → 区分疾病和症状 → ICD标准术语
步骤4：标记不良反应 → 判断严重程度 → 归类受累系统
步骤5：识别禁忌人群/情况 → 区分绝对禁忌和相对禁忌
步骤6：构建实体间关系 → 在原文中寻找证据 → 评估置信度
步骤7：汇总输出 → JSON格式
```

#### 优势
- ✅ **复杂抽取准确率高**：推理链提升了多步关系和隐式关系的识别
- ✅ **可解释性强**：推理过程可追溯
- ✅ **错误易定位**：推理步骤出错可以针对性修正

#### 劣势
- ❌ **Token消耗高**：推理过程占据大量输出Token
- ❌ **响应时间长**：多步推理增加延迟
- ❌ **输出格式不保证**：推理文本和JSON混在一起

#### 实测数据
| 指标 | 得分 |
|------|------|
| 实体F1 | 0.87 |
| 关系F1 | 0.82 |
| Schema合规率 | 75% |
| 平均Token消耗 | 3,200 |

#### 适用场景
- 复杂关系抽取（如药物多步相互作用链）
- 含隐式表达的文本（如"可能增加...风险"）
- 需要输出可解释性的审核场景

### 2.3 策略三：结构化JSON输出

#### 设计原理
通过严格定义输出JSON Schema，限制模型必须按指定格式输出。

#### Schema设计要点
1. **必填字段标记**：在Schema中明确标注`required`
2. **字段类型约束**：string / number / boolean / array
3. **取值范围约束**：enum约束（如 severity: ["轻度", "中度", "重度"]）
4. **嵌套结构规范**：明确层级关系

#### 优势
- ✅ **格式100%可控**：严格Schema约束
- ✅ **程序化处理友好**：直接JSON解析
- ✅ **质量自检容易**：Schema验证即可发现格式错误
- ✅ **多模型一致性好**：不同模型输出结构统一

#### 劣势
- ❌ **Prompt设计成本高**：Schema需要精心设计
- ❌ **灵活性低**：Schema变更需同步更新所有下游
- ❌ **模型可能遗漏**：过于严格的约束可能抑制模型"思考"

#### 实测数据
| 指标 | 得分 |
|------|------|
| 实体F1 | 0.90 |
| 关系F1 | 0.84 |
| Schema合规率 | 98% |
| 平均Token消耗 | 2,100 |

#### 适用场景
- ⭐ **生产环境（推荐）**
- 需要批量自动化处理
- 下游系统强依赖固定格式
- 多模型并行标注需要一致性

## 3. 核心设计原则

### 3.1 角色设定原则

❌ **差的角色设定**：
> "你是一个AI助手，请帮我从文本中抽取信息。"

✅ **好的角色设定**：
> "你是一位资深的医药信息学专家，拥有10年以上临床药学经验，擅长从医药文献中精确抽取结构化信息。你对WHO ATC药品分类体系和ICD-11疾病分类体系非常熟悉。"

**关键要素**：
- 明确的专业领域（"医药信息学专家"）
- 量化的经验描述（"10年以上"）
- 具体的能力描述（"擅长从...抽取..."）
- 知识体系锚定（"熟悉ATC和ICD"）

### 3.2 约束明确原则

❌ **模糊约束**：
> "请尽量准确地标注。"

✅ **明确约束**：
> "对于每个药品实体：(1)必须使用中国药典通用名；(2)必须标注ATC分类；(3)必须在原文中找到mention；(4)如果分类不确定，标注'未分类'而非猜测。"

### 3.3 输出格式锁定原则

✅ **推荐的Schema锁定技术**：
1. 在System Prompt中附完整的JSON Schema
2. 用代码块明确展示期望格式
3. 最后一句强调"只输出JSON，不要任何其他文字"
4. 添加结构验证提示："输出前请自行验证JSON格式有效性"

### 3.4 领域知识注入原则

在Prompt中注入医药领域的专业规则：

```
实体标准化规则:
- "HP" → "幽门螺杆菌"
- "扑热息痛" → "对乙酰氨基酚"（通用名优先）
- "CAD" → "冠心病"

关系判断规则:
- "用于治疗XX" → indication关系
- "可能引起XX" → adverse_effect关系（confidence=0.7，因为是可能性描述）
- "禁用" → contraindication关系
- "与XX合用" → drug_interaction关系
```

### 3.5 迭代优化方法论

```
1. 编写初版Prompt
2. 标注10条测试文本
3. 分析错误模式：
   ├─ 类型A: 格式错误 → 强化格式约束
   ├─ 类型B: 遗漏实体 → 补充示例或明确触发词
   ├─ 类型C: 错误标注 → 增加反面示例
   └─ 类型D: 边界识别偏差 → 细化边界规则
4. 针对性修改Prompt
5. 用新Prompt重新标注 → 对比F1变化
6. 重复2-5直到F1稳定
```

## 5. 踩坑记录

### 坑1：模型对"可能"的理解偏差
**现象**：模型常将"可能引起XX"直接标注为确定的adverse_effect关系，遗漏了"可能"表示的不确定性。
**解决**：在Prompt中增加概率性表述的处理规则：标记为adverse_effect但降低confidence至0.7。

### 坑2：药品商品名和通用名的混淆
**现象**：同一药品在不同文档中以不同名称出现，导致知识库中出现重复条目。
**解决**：在Prompt中内置药品同义名映射表，要求模型始终输出通用名，同时在kb_builder中做二次实体对齐。

### 坑3：JSON输出被截断
**现象**：长文本标注时模型输出被token限制截断，JSON不完整。
**解决**：(1)增加max_tokens至4096；(2)对超长文本先分段再标注；(3)增加JSON完整性自检步骤。

### 坑4：结构化约束"过度限制"
**现象**：过于严格的Schema导致模型不敢标注不确定的实体，Recall下降。
**解决**：在Schema中加入confidence字段，允许标注不确定实体但标记置信度。
