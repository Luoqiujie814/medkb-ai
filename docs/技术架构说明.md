> 版本: v1.0 | 更新日期: 2025-05-29 | 作者: 罗秋杰

## 1. 系统概述

MedKB-AI 是一个面向医药领域的AI知识治理平台，实现从多源异构语料采集、数据清洗、LLM辅助信息抽取与标注到结构化知识库构建与智能问答的完整闭环。系统旨在解决医药信息分散、异构、非结构化的痛点，为大模型在医药垂直领域的应用提供高质量结构化知识支撑。

### 1.1 设计目标

- **知识治理全链路**：覆盖采集→清洗→标注→建库→校验→查询六个阶段
- **LLM深度融合**：基于大语言模型进行命名实体识别（NER）和关系抽取（RE）
- **多策略提示词工程**：支持Few-shot、Chain-of-Thought、结构化JSON输出三种策略
- **自动化质量保障**：内置8项质检规则，覆盖完整性、一致性、准确性
- **可复现流水线**：每个阶段独立可执行，输入输出标准化

### 1.2 技术栈

| 层次 | 技术选型 | 说明 |
|------|---------|------|
| 编程语言 | Python 3.10+ | 全栈开发语言 |
| LLM API | Anthropic Claude / OpenAI GPT / DeepSeek | 多模型支持，可切换 |
| 数据库 | SQLite 3 | 轻量级关系型数据库，零配置 |
| 数据处理 | pandas, numpy | 数据框操作和数值计算 |
| 文本处理 | jieba, re, beautifulsoup4 | 中文分词和文本清洗 |
| 评估工具 | scikit-learn | 分类指标计算 |
| 测试框架 | pytest | 单元测试和质量测试 |

### 2.2 核心模块说明

#### 2.2.1 语料采集模块 (scraper.py)
- **职责**：从多源渠道采集医药文本语料
- **支持源**：NMPA药品说明书、PubMed文献摘要、临床诊疗指南
- **内置样本**：5篇高质量医药语料（药品说明书+指南+综述）
- **去重机制**：基于SHA256内容哈希去重
- **输出**：标准化JSON格式 → `data/raw/corpus_sample.json`

#### 2.2.2 数据清洗模块 (cleaner.py)
- **职责**：文本规范化、去噪、分句、质量检测
- **清洗流水线**：
  1. HTML标签和控制字符去除
  2. 全角→半角标点转换
  3. 空白字符规范化
  4. 医药术语标准化（如"HP"→"幽门螺杆菌"）
  5. 中文分句（按句号/换行等边界）
  6. 质量评分（A/B/C三级）
- **输出**：`data/cleaned/corpus_cleaned.json`

#### 2.2.3 LLM标注模块 (annotator.py)
- **职责**：基于大模型进行NER和RE
- **多模型支持**：Claude / GPT / DeepSeek / Mock
- **三种Prompt策略**：
  - Few-shot (3示例)：快速冷启动
  - Chain-of-Thought：复杂推理
  - 结构化JSON输出：生产环境推荐
- **标注流程**：实体抽取 → 关系抽取（两阶段Pipeline）
- **输出**：`data/annotated/corpus_annotated_*.json`

#### 2.2.4 知识库构建模块 (kb_builder.py)
- **职责**：将标注结果转化为结构化SQLite知识库
- **实体对齐**：药品同义名合并（如"扑热息痛"→"对乙酰氨基酚"）
- **8张核心表**：drugs, diseases, indications, adverse_effects, drug_interactions, source_docs, annotation_log, quality_checks
- **双模式**：标注结果构建 + 结构化JSON直接导入

#### 2.2.5 质量校验模块 (validator.py)
- **8项质检规则**：
  1. 药品名称重复检测
  2. 疾病名称重复检测
  3. 适应症关系冲突检测
  4. 必填字段完整性
  5. 外键引用完整性
  6. 不良反应信息完整度
  7. 药物相互作用等级标注
  8. 标注一致性评估
- **输出**：质检报告 + 数据库质检记录

#### 2.2.6 知识检索模块 (query_engine.py)
- **查询方式**：药品查询、疾病查询、相互作用查询、全文搜索
- **输出格式**：CLI终端展示 + JSON/CSV导出

## 4. 数据库设计

### 4.1 ER图（概念模型）

```
  ┌──────────┐       ┌──────────────┐       ┌──────────┐
  │  drugs   │──────→│ indications  │←──────│ diseases │
  │  药品表   │       │   适应症关系   │       │  疾病表   │
  └──────────┘       └──────────────┘       └──────────┘
       │                                              
       ├──────→ adverse_effects (不良反应)              
       │                                              
       ├──────→ drug_interactions (药物相互作用)        
       │                                              
       └──────→ source_docs (来源文献)                  
                                                      
  annotation_log (标注日志) ← 记录每次标注操作的元数据     
  quality_checks (质检记录) ← 记录所有质检问题            
```

### 4.2 核心表设计原则

1. **范式化设计**：遵循第三范式(3NF)，消除数据冗余
2. **外键约束**：保证引用完整性
3. **唯一约束**：防止重复数据（如UNIQUE(drug_id, disease_id)）
4. **索引优化**：高频查询字段建立索引
5. **溯源能力**：每条记录关联 source_doc_id 和 annotator_model

详细Schema见 `db/schema.sql`。

## 5. 关键设计决策

### 5.1 为什么选择SQLite而非MySQL？

- ✅ 零配置，适合单机部署和快速原型
- ✅ 文件型数据库，便于版本管理和迁移
- ✅ 对于知识库读多写少的场景足够高效
- ✅ 项目定位为demo/MVP，SQLite降低了使用门槛

### 5.2 为什么标注采用两阶段Pipeline？

将NER和RE分两个阶段而非一次性完成：
- 优点：每个阶段职责清晰，便于调试和Prompt优化；可独立切换策略对比效果
- 缺点：多一次API调用，增加延迟和Token消耗
- 权衡：对于质量要求高的知识治理场景，两阶段更可控

### 5.3 Mock模式的设计考虑

提供不依赖API Key的Mock模式：
- 基于规则匹配模拟LLM输出
- 便于CI/CD环境中自动化测试
- 降低入门门槛：用户可以零成本运行完整流水线

## 6. 性能指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 单文档清洗耗时 | < 1s | 主要耗时为文本处理和分句 |
| 单文档LLM标注耗时 | < 5s | 取决于API响应速度 |
| 知识库构建耗时 | < 3s | SQLite批量插入 |
| 查询响应时间 | < 100ms | 索引优化后的简单查询 |
| 实体抽取F1 | > 0.85 | 结构化JSON策略 |
| 关系抽取F1 | > 0.80 | 结构化JSON策略 |

## 7. 后续演进方向

1. **知识图谱化**：从关系型存储升级为图数据库（Neo4j），支持更复杂的关系遍历
2. **增量更新机制**：支持增量添加新语料，而非全量重建
3. **Web可视化界面**：FastAPI + 前端展示知识网络
4. **RAG集成**：将结构化知识库作为大模型RAG（检索增强生成）的数据源
5. **多语言扩展**：支持英文医学文献的语料处理和知识抽取
